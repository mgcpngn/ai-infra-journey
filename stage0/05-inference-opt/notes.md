# 第 5 步笔记：给自己的小 GPT 做推理优化

完整实测见 [results.md](results.md)，代码见 [infer_tang.py](infer_tang.py)。模型：6 层 6 头 384 维，block 256，RTX 4060 Laptop，fp32。

## 四个最重要的发现

### 1. KV cache 要在"计算真的贵"的时候才有用

| 场景 | 无 cache → 有 cache |
| --- | --- |
| GPU batch=1 | 1.77 s → 1.96 s（0.9 倍，反而慢一点） |
| GPU batch=128 | 24.8 s → 1.6 s（15 倍） |
| CPU batch=1 | 10.7 s → 1.3 s（8 倍） |

- 结果一字不差：cache 只是把算过的 K、V 存起来，数学上没变。
- GPU 小 batch 时时间花在发射几百个小 kernel 上，算多算少差不多，所以 cache 省下的计算看不出来。batch 大到 32 以上，或者换到没有发射开销的 CPU，重算的代价才露出来。
- 没 cache、batch=128 时，第 10 / 100 / 250 步分别是 7.5 / 71 / 203 ms，随长度线性变慢，这就是"重算"的代价。

### 2. prefill 和 decode 是两种完全不同的活

- prefill 一次处理 200 字：7.3 ms（≈ TTFT）
- decode 每生成 1 字：6.6 ms（≈ TPOT）
- 平摊到每个字，prefill 比 decode 便宜约 180 倍。GPU 处理 200 个字和 1 个字几乎同价：瓶颈是固定开销和读一遍权重，不是算力。

### 3. 大 batch 时，显存是被 KV cache 吃掉的，不是模型

| batch | KV cache | 和模型参数（65 MB）比 |
| --- | --- | --- |
| 1 | 4.5 MB | 0.07 倍 |
| 32 | 144 MB | 2.2 倍 |
| 128 | 576 MB | 8.9 倍 |

公式 2 × 层数 × batch × 长度 × 384 × 4 字节，和实测分毫不差。

batching 让吞吐从 298 涨到 27,125 字/秒（91 倍），每条请求延迟只从 0.86 s 涨到 2.4 s。这个小模型远没吃满 4060，加 batch 几乎白赚。

### 4. 变小 ≠ 变快

| 方法 | 文件 | loss 变化 | 速度 |
| --- | --- | --- | --- |
| int8 只存权重 | 65.5 → 26.2 MB | +0.0002 | 慢 1.4～1.6 倍（每次要先还原成 fp32） |
| int8×int8 + torch.compile | | +0.0014 | 大 batch 整遍前向快 2.17 倍 |
| fp8×fp8 + torch.compile | | +0.0013 | 大 batch 整遍前向快 1.69 倍 |

- 量化几乎不伤效果：5 首诗在四种精度下完全相同。
- 只有让 tensor core 直接用低精度算、再把零碎小算子融合起来，才真的变快；而且只在大矩阵（prefill、大 batch）上快。decode 每步矩阵太小，反而更慢。

## 代码导读：[infer_tang.py](infer_tang.py)

| 位置 | 做什么 |
| --- | --- |
| 第 51–55 行 | KV cache 本体：新字的 K、V 写进预先分配好的缓冲区，注意力看"缓存里的旧字 + 新字" |
| 第 96–97 行 | 生成时只算最后一个位置的输出，省掉 (batch, 长度, 词表) 那张大表（之前爆显存的原因） |
| 第 130–134 行 | 第一步整段喂进去（prefill），之后每步只喂最新的一个字（decode） |
| `QLinear` | weight-only int8：权重存 int8，算之前还原成 fp32 |
| `W8A8Int8`、`W8A8Fp8` | 权重和输入都量化，用 tensor core 直接算 int8×int8、fp8×fp8 |
| 全程 fp32、关 TF32 | 保证有/无 cache 的结果能一字不差地比对 |

## 状态

✅ 第 5 步过关（10-16）。

检查题回顾：
- **batch 为什么不能开到最大**：两道上限。一是显存（大头是 KV cache，batch=128 时 576 MB，是模型的 8.9 倍）；二是延迟（batch 1→256，吞吐涨 91 倍，每条请求的等待变成 2.8 倍）。机器越划算，每个用户越慢。
- **Qwen3-8B、32K 上下文的 KV cache**：只记一句——每个字，在每个块里，存一份 K 和一份 V。一个字 = (4096+4096) × 36 块 × 2 字节 ≈ 0.56 MB；32K 字 ≈ 18 GB。模型本身 ≈ 16 GB，24 GB 卡一个用户都装不下。Qwen3-8B 用 GQA（4 个头共用一份 K/V，每份 1024 个数，凭记忆，待核对 config.json）→ 约 4.5 GB/用户，能装 1 个。
- 结论：上下文越长、用户越多，KV cache 通常比模型本身更早占满显存。
