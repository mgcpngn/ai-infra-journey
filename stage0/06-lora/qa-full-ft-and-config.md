## 1. 全量微调和预训练

「新词」**全量微调**：从一个已经训练好的模型开始，用少量数据继续训练，模型里所有参数都改。

两者每一步做的事完全一样：读一段字 → 算 loss → 算每个参数该怎么改 → 改所有参数。
区别只在三处：

| | 预训练 | 全量微调 |
|---|---|---|
| 从哪里开始 | 随机的参数 | 别人预训练好的参数 |
| 数据 | 海量网页、书（Qwen3 说是约 36 万亿 token，凭记忆，未核实） | 你的 13,975 首绝句（约 50 万 token，推测） |
| 学习率 | 大（例如 3e-4，凭记忆，未核实） | 小（你跑的是 1e-5），怕把学会的东西改坏 |

你已经做过两种：
- 第 4 步 gpt_tang.py = 预训练：小 GPT 从随机参数开始。
- 第 6 步实验 2 = 全量微调：从 Qwen 的参数开始（lora_poem.py:127 `from_pretrained`）。

验证实验见最后。

## 2. 全量微调的显存

一句话：**每个参数要存几份，每份几个字节，加起来再乘 596M。**

| 存什么 | 每个参数几字节 | 596M 个参数一共 |
|---|---|---|
| 参数本身（bf16） | 2 | 1.11 GB |
| 每个参数该怎么改（梯度，bf16） | 2 | 1.11 GB |
| AdamW 给每个参数记的两个数（fp32） | 4 + 4 | 4.44 GB |
| 一份 fp32 的参数（改的时候用，不丢精度） | 4 | 2.22 GB |
| 合计 | 16 | **8.88 GB**（还不算中间结果） |

- 最占显存的是 AdamW 的两个数：4.44 GB，占一半。
- 你实测 5.60 GB 跑通，是因为 PyTorch 默认让 AdamW 的两个数也用 bf16，也没有 fp32 那份：2+2+2+2 = 8 字节 → 4.44 GB，再加中间结果 → 5.60 GB。代价是改参数时丢精度。
- LoRA 只给 2,293,760 个参数存梯度和 AdamW 的数，所以这部分几乎为零。

## 3. config.json 逐项

### 决定模型大小的（要懂）
| 字段 | 值 | 用我们的词 | 小 GPT 里对应 |
|---|---|---|---|
| vocab_size | 151936 | 字表有 151936 个 token | 8182 |
| hidden_size | 1024 | 每个字的数 = 1024 | 384 |
| num_hidden_layers | 28 | 28 层 | 6 |
| num_attention_heads | 16 | 每层 Q 有 16 个头 | 6 |
| head_dim | 128 | 每个头 128 个数 | 64 |
| num_key_value_heads | 8 | K、V 只有 8 个头，每 2 个 Q 头共用 1 组 K/V（GQA） | 6（不共用） |
| intermediate_size | 3072 | 每层 MLP 先把 1024 个数放大到 3072 个，再变回 1024 | 1536 |
| max_position_embeddings | 32768 | 上下文长度 32768 | 256 |
| tie_word_embeddings | true | 输入查表和输出打分共用一张表 | — |
| torch_dtype | bfloat16 | 每个数 2 字节 | — |

注意：16 头 × 128 = 2048，比每个字的数 1024 还多。所以「头把每个字的数平分」只在小 GPT 里成立（6 × 64 = 384）。

### 用这些数数出 596M 参数
- 每层注意力：Q 表 1024×2048 + K 表 1024×1024 + V 表 1024×1024 + 输出表 2048×1024 = 6,291,456
- 每层 MLP：3 张表 × 1024×3072 = 9,437,184
- 每层合计（加上很少的 norm 参数）：15,730,944；× 28 层 = 440,466,432
- 字表那张表：151936 × 1024 = 155,582,464（输入、输出共用，只算一次）
- 总共 596,049,920 ≈ **596M**，和你的输出一样。
- × 2 字节 = 1137 MB，和你的模型文件一样。
- 如果 tie_word_embeddings 是 false，要多一张 1.56 亿参数的表。

### 用这些数算 KV cache
每个字，在每层里，存一份 K 和一份 V：28 层 × (1024 + 1024) 个数 × 2 字节 = 112 KB / 字。
32768 字 × 112 KB = 3.5 GB / 用户。如果 K/V 也是 16 头（不共用），要 7 GB。

### 其他字段（现在不用管）
| 字段 | 一句话 |
|---|---|
| bos_token_id / eos_token_id = 151643 | 「开始」「结束」这个 token 在字表里的编号。pad 也用它，所以你日志里有 attention mask 的警告 |
| use_cache = true | 生成时开 KV cache |
| hidden_act = silu | MLP 里用的一个函数 |
| rms_norm_eps | 防止除以 0 的小数 |
| rope_theta、rope_scaling | 告诉模型每个字在第几个位置的方法 |
| initializer_range = 0.02 | 随机参数从多大的范围里取（预训练从这里开始） |
| attention_bias、attention_dropout | 注意力里不加偏置、训练不随机丢数 |
| sliding_window、use_sliding_window、max_window_layers | 只看最近一段字的功能，这里关着 |
| architectures、model_type、transformers_version | 告诉代码用哪个类来建模型 |

## 4. 验证实验：只改「从哪里开始」

提示词（给本地 Claude Code）：

```
在 lora_poem.py 旁边写 pretrain_vs_ft.py，复用它的数据、encode、val_loss。
只比一个变量：起始参数。
A：AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-0.6B-Base")（全量微调）
B：AutoModelForCausalLM.from_config(同一个 config)（随机参数，等于预训练的第一步）
两个都用 bf16、AdamW lr=1e-5、batch=4、长度 64、300 步、同一个数据顺序。
打印：第 0 步和每 100 步的验证 loss；训练完各用种子 1234 生成「山中桂」一首。
每跑完一个就 del 模型、清显存。
```

预测：
- B 第 0 步验证 loss ≈ 11.93（= ln 151936，在 151936 个 token 里平均地瞎猜）；A 第 0 步 ≈ 4.58（就是基线）。
- 300 步后：A 降到 4 以下；B 还在 7 以上，写不出诗。
- 结论应该是：同样的代码、同样的步数，差别全部来自起始参数。预训练花的钱买的就是这些参数。
