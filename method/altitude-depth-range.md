## 一、高度：先看最终结果，再看眼前这一步

### 现在的样子
- 路线图按「步」排。每一步问的是「这个概念是什么」。
- 这几天陷进了训练的细节。这是你自己说的：「我感觉自己陷入到这些概念中去了」。
- 每一步做完，看不出最终目标近了多少。

### 问题在哪
- 最终目标写的是「懂」「能设计」「能讲清楚」。这些词没法检查。
- 没有一样东西，能把 1 到 7 步的结果串起来。

### 怎么改
1. **把最终目标写成一份能交出去的报告。** 报告回答 5 个问题：
   - 给一个模型、一种卡、一个用户量，能同时服务多少个用户？
   - 每个用户等第一个字要多久？之后每个字要多久？
   - 每生成一百万个 token 花多少钱？
   - 瓶颈在哪里？
   - 换什么（卡、方案、参数）能改善？多少？
   第 3 月的「假想客户方案」就是这份报告的完整版。
2. **建一个账本（ledger.md）。** 每一步都填同一组数：
   参数个数、显存、第一个字的时间、每个字的时间、每秒总共出多少字、瓶颈判断。
   第 0 阶段已经测过的数，补进去。到第 3 月，这个账本就是报告的底稿。
3. **学每个概念前，先问一句：它改变账本里的哪个数？** 改变不了的，放进暂存区。
   - LoRA：不合并时，每个字多一点计算；一个原模型可以挂好几个 LoRA。
   - DPO：只改训练的花费。推理的账本不变（推测）。
   - bf16：参数的显存减一半。
4. **每周倒推一次。** 看报告里还缺哪一格数。下周就补这一格。

## 二、深度：顺着数字往下挖，挖到数据、工具和那一行代码

### 现在的样子
- 跑脚本，看输出，对答案。
- 已经有一次专家式的深挖：模板化的开头，最后找到了 `lora_poem.py:156`，那一行每首诗都把随机种子重设成 1234。

### 问题在哪
- 多数数字只是记下来了，没有问：为什么是这个数？最好能到多少？

### 怎么改
深度不是更多公式。深度是看真实的数据、真实的工具输出、真实的代码。

1. **每个测出来的数，配一个天花板。** 天花板 = 按卡的说明书，理论上最快能到多少。
   - 电脑算天花板，你只预测：实测离天花板远还是近？
   - 例：decode 每出一个字，要把全部参数从显存读一遍。所以每个字的时间有一个下限，由「参数多少」和「显存读得多快」决定。
   - 离天花板远，说明有东西在浪费。你的 torch.compile 快了 1.48 倍，就是少浪费了一部分。
2. **异常时，不换参数重跑，先找到那一行。** 结果反常，就找到造成它的那一行代码或那一条数据。随机种子那次就是范例。这一条写进 README 的学习规则。
3. **读工具自己的原话。** vLLM 的启动日志、nvidia-smi 打印的数，直接读，不看别人的总结。第 1 月的 vLLM 基线已经安排了读 KV cache 大小。
4. **看几条数据本身。** 例：第 7 步 DPO 的「差的诗」是随便挑的另一首。训练前，先打印 5 对看看。模型可能只学会「看题目里的字」。
5. **每个阶段看一次时间花在哪里。** 用一个工具，把一步里每个算子花的时间列出来。这个工具的名字等用到时再学。

## 三、广度：借别的学科已经有的答案

### 现在的样子
- 主要从机器学习的角度学。
- 日常比方效果最好：碗里的小球、刻度尺、存零钱。你一看就懂了。

### 怎么改
1. **借排队的学问（银行窗口、餐厅）。** 推理服务就是排队：
   - batch = 厨师一锅同时炒几份。
   - 第一个字的时间 = 排队 + 点菜 + 第一道菜上桌。
   - PD 分离 = 后厨分成两组，一组备菜（prefill），一组炒菜（decode）。
   - 第 2 月学 PD 分离前，先在网页里模拟一个餐厅，看什么时候分两组更快。
2. **借操作系统的内存分页。** vLLM 存 KV cache 的方法，借的就是操作系统管内存的方法（凭记忆，未核实）。学 vLLM 时先看这个比方。
3. **借仓库物流。** 卡算得快，但搬数据慢。很多优化是少搬几趟货。
4. **借工厂算账。** 一块卡就是一台机器。开工率、每件货的成本，就是每百万 token 的成本。
5. **借学习的学问。** vocab.md 里每个词，学完后第 1 天、第 3 天、第 7 天各再问你一次。
6. **借两种卡对照。** 硬件表里有昇腾 910B，但还没用过。同一个实验在 4060 和 910B 上各跑一次，看换卡后哪些数变了。这就是「硬件适配」要回答的问题。
7. **借你本行的经验。** 告诉我你的本行，我用它做比方。
