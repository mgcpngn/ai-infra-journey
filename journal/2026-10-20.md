## 问答：6 亿个参数，怎么衡量总体 loss？
- 用户问：6 亿个参数怎么确保每个都有最好的 loss？总体 loss 怎么衡量才合理？
- 更正：我上次说「6 亿个小球同时在走」不准，会让人以为每个参数有自己的碗和 loss。正确：整个模型只有一个 loss，6 亿个参数共用。
- loss = 猜下一个字猜得多差，所有位置扣分取平均（第 6 步 4.58 → 4.08）。
- 调音台比方：6 亿个旋钮 = 参数；loss = 整首歌多难听（一个分数）；梯度 = 每个旋钮往哪拧、影响多大；一步 = 所有旋钮一起拧，各拧 学习率 × 自己的提示。碗里的小球 = 单独拿出一个旋钮看。
- 不需要每个参数单独最好；衡量合理看验证 loss（没见过的诗），对比过拟合。
- 检查题：一步里旋钮一个一个拧还是一起拧？每个拧多少由什么决定？
- 用户答：「6 亿个旋钮一起拧，每个拧多少由学习率决定，梯度由模型和数据决定」→ 一起拧 ✅、梯度来源 ✅；「拧多少」不完整：学习率大家共用，只由它决定会全都一样；每个旋钮拧的量 = 学习率 × 自己的梯度。
- 用户再答：「每个旋钮方向和拧多少不一样，但拧的时机一致，同步实施」→ 过关 ✅。补：同时拧 6 亿个 = GPU 擅长的并行计算。

## vLLM 基线结果（stage1/01-vllm-baseline/results.md）
- N=1 每字 6.03 ms，天花板 5.73 ms（实测带宽 208 GB/s），1.05 倍。第 7 步脚本 129 ms → 同模型同卡快 21 倍：那 28 倍差距是程序怎么驱动 GPU 造成的，不是卡本身。
- 更正：我之前的天花板 4.7 ms 是按说明书 256 GB/s 算的；实测带宽 208 GB/s，天花板是 5.73 ms。
- N 1 → 64：总吞吐 33 倍，每字 1.8 倍，首字 4.3 倍（和小 GPT batching 一样的规律）。
- KV cache 4.61 GiB = 43,120 token，和 112 KB/token 算出的 43,160 对上；每请求 191 token → 约 225 个能同时放下。
- 账本已填两行。
- 用户预测「vLLM 很快，应该接近 4.7 ms」→ 对 ✅（6.03 ms，贴着实测天花板 5.73 ms）。
- 留给下班前：1000 个请求同时来会怎样（KV cache 只够约 225 个）；3 句收获。
- 用户答 1000 个请求：「显存会溢出吧；vLLM 有队列；最大并发 21 是不是不排队最多 21 个；不知道怎么算」→ 队列 ✅；溢出 ✗（启动时 KV cache 一次占好 4.61 GiB，放不下就排队）；21 = 每个请求都写满 2048 token 时的最坏情况（43,120 ÷ 2048）；191 token 的请求约 225 个。
- 停车场比方：43,120 个车位，一个 token 一个车位；大巴（2048）停 21 辆，小车（191）停约 225 辆；其余在门口排队，首字时间变长。
