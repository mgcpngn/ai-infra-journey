## 结论（对照预期）

**实验 1 KV cache 正确性**：预期两种方式结果完全一样，因为 cache 只是把算过的 K、V 存起来，数学上没变。实测 5 个开头、各 200 字全部一字不差（全程 fp32，关掉 TF32，避免舍入差异让 argmax 翻转）。

**实验 2 速度**：预期没 cache 时第 t 步要重算 t 个字，越往后越慢；有 cache 每步只算 1 个字，耗时是平的。
- 和预期一致的部分：GPU batch=128 没 cache 时第 10/100/250 步是 7.5 / 71 / 203 ms，基本随长度线性增长；有 cache 后一直是几 ms，整体快 15 倍。CPU 上 batch=1 和 8 都快 8~17 倍。
- 和预期不一致的部分：GPU batch=1、8 时 cache 没有加速（0.9x）。原因是这个模型太小，GPU 上每一步的耗时主要花在 CPU 发射几百个小 kernel 上（WSL 下这一步更慢），不在计算本身。所以从 batch=1 到 128，有 cache 时每步都是 6~10 ms。cache 省下来的计算量要等 batch 大到计算真正成为瓶颈（≥32）才显现。cache 路径每层还多两次写缓存的拷贝，小 batch 时反而略慢。
- CPU batch=1 有 cache（5 ms/步）比 GPU（7.7 ms/步）还快，也是因为启动开销：CPU 没有发射 kernel 的成本。
- 要在小 batch 下榨干 GPU，下一步可以用 CUDA Graph / torch.compile 把一步的几百个 kernel 合成一次发射。

**实验 3 prefill vs decode**：预期 prefill 一次处理 200 个字，几乎和 decode 一个字一样快。实测 prefill 7.3 ms（TTFT），decode 每字 6.6 ms（TPOT），平摊到每字 prefill 只要 0.037 ms，相差约 180 倍。说明 GPU 处理 200 个字和处理 1 个字几乎同价，瓶颈是固定开销和读权重，不是算力。

**实验 4 显存**：预期实测和公式一致（cache 是一次性预分配的）。实测 4.5 / 144 / 576 MB，和公式分毫不差。batch=128 时 KV cache 是模型参数的 8.9 倍。大 batch 推理时显存主要被 cache 占掉，不是模型。

**实验 5 batching**：预期吞吐随 batch 上升，每条请求的延迟也跟着上升。实测吞吐从 298 涨到 27,125 字/秒（91 倍），延迟只从 0.86 s 涨到 2.4 s。这个小模型在 4060 上还远没吃满算力，所以加 batch 几乎是白赚的吞吐。GPU 计时有抖动（batch=4 和 64 延迟接近），但趋势明确。

**实验 6 int8**：预期文件约缩到 1/4、loss 几乎不变、速度可能变慢。实测文件 65.5 → 26.2 MB（embedding 8182×384 仍是 fp32，约 12 MB，所以不到 1/4）。验证 loss 4.7338 → 4.7340（+0.0002），5 首诗完全相同。速度变慢 1.4~1.6 倍：普通 PyTorch 没有 int8×fp32 的矩阵乘算子，每次前向都要先把每层 int8 权重还原成 fp32（多一次读写 + 多一次 kernel 发射），再做同样的 fp32 矩阵乘。int8 只省了存储，没省计算。要真正提速，需要把反量化融合进矩阵乘的 kernel（如 Triton / bitsandbytes 那类实现），或者用 int8×int8 的 `torch._int_mm`。

注：GPU 小 batch 计时受 kernel 启动开销影响，每次运行会有 ±30% 抖动。

## 实验 7：int8 / fp8 矩阵乘（有 cache，生成 255 字；括号里是相对 fp32 的加速）

| 方法 | 验证集 loss | 比 fp32 | 验证集整遍前向 s | 同上 + torch.compile s | batch=1 ms | batch=64 ms | batch=256 ms |
|---|---|---|---|---|---|---|---|
| fp32 | 4.7338 | +0.0000 | 2.36（1.00x） | 2.10（1.00x） | 1930.87（1.00x） | 1133.39（1.00x） | 1488.47（1.00x） |
| int8 只量化权重（实验 6） | 4.7340 | +0.0002 | 2.48（0.95x） | 2.21（0.95x） | 1741.92（1.11x） | 2575.83（0.44x） | 2384.26（0.62x） |
| int8×int8（_int_mm） | 4.7351 | +0.0014 | 2.93（0.81x） | 0.97（2.17x） | 3610.81（0.53x） | 5867.08（0.19x） | 3790.53（0.39x） |
| fp8×fp8（_scaled_mm） | 4.7350 | +0.0013 | 2.41（0.98x） | 1.24（1.69x） | 4118.99（0.47x） | 4139.50（0.27x） | 3974.43（0.37x） |

「验证集整遍前向」每次喂 64×256 个字，是计算量最大、最能体现 tensor core 的场景；生成时每步只喂 batch 个字，小 batch 主要卡在 kernel 发射开销。int8×int8 / fp8×fp8 每层要先量化输入（多几个小 kernel），再矩阵乘、再乘回缩放系数；不融合时这些逐元素操作的耗时超过矩阵乘省下的时间，torch.compile 融合后才显出 tensor core 的优势。生成那几列没有 compile（每步 cache 长度在变，会反复重新编译）。

**实验 7 结论**：4060（Ada 架构，算力等级 8.9）原生支持 int8 和 fp8 tensor core，PyTorch 2.13 已经带了对应算子 `torch._int_mm` 和 `torch._scaled_mm`，不用升级。
- 精度：权重和输入都量化后，loss 只多 0.0013~0.0014，5 首诗和 fp32 完全相同。
- 矩阵乘本身确实快：profile 一个 64×256 batch，fp32 的线性层矩阵乘约 54 ms，int8 的 `_int_mm` 只要 6.8 ms。
- 不融合时整体反而更慢（0.8x），因为量化输入、乘回缩放系数、切掉补齐的维度这些逐元素操作，每个都要把大张量完整读写一遍，加起来约 75 ms，比省下的还多。
- 用 `torch.compile` 把这些小操作融合进少数几个 kernel 后，整遍前向 int8 快 2.17 倍、fp8 快 1.69 倍。这是 tensor core 真正发挥作用的场景（大 batch 的 prefill、验证集评估）。
- 生成（decode）没有提速，还慢 2~5 倍：每步只喂 batch 个字，矩阵太小，瓶颈本来就是 kernel 发射开销（见实验 2），量化又多了好几个小 kernel。要让 decode 也受益，需要 CUDA Graph（`torch.compile(mode="reduce-overhead")` 配合固定形状的 cache）或者手写融合 kernel。
- 生成那几列的 GPU 计时抖动很大（比如这次 fp32 batch=64 是 1.1 s，上次是 2.4 s），只看趋势。
