# 第 5 步：给自己的小 GPT 做推理优化

## 这一步要搞懂的
- KV cache：把算过的东西存起来，不再重算。它省了什么、花了什么（显存）
- prefill 和 decode：处理 prompt 和一个字一个字往外生成，为什么快慢完全不同
- batching：一次生成很多条，为什么单条更便宜、但每条可能更慢
- 量化：把参数从 4 字节压到 1 字节，模型变小，效果损失多少

上一步发现：batch=1 时，这个小模型重算几乎不花时间。所以这一步每个实验都要在不同 batch 下测，才看得到 KV cache 真正的作用。

## 给本机 Claude Code 的提示词

```
先用大白话讲每个实验在干什么、预期会看到什么，再写代码。每个实验打印一张表。

在第 4 步的小 GPT 上做推理优化。读取 checkpoints/ 里训练好的模型（block_size、层数等从 checkpoint 里读，不要写死），在我的 RTX 4060（8GB）上测。不要用 vLLM、HuggingFace 等现成的推理库，自己实现。

1. KV cache：给注意力加上 KV cache，生成时每一步只算新的那个字。
   - 正确性：temperature=0（每步取概率最大的字），同一个开头，有 cache 和没 cache 生成 200 个字，必须一字不差。打印对比结果。
   - 注意生成长度不要超过 block_size（超过要截断，cache 也要跟着处理，先简单做：只生成到 block_size 为止）。

2. 速度对比：有 cache vs 没 cache，生成到 block_size 个字。batch 分别取 1、8、32、128（每条用不同的开头字），打印每种情况的总耗时、平均每步耗时、每秒总共生成多少字。GPU 测完，再在 CPU 上测 batch=1 和 batch=8。
   - 另外打印：没 cache 时，第 10 步、第 100 步、第 250 步各自耗时多少（看重算的代价是不是随长度增长）。

3. prefill 和 decode：用一段 200 字的唐诗当 prompt，batch=1，有 cache。
   - 分别测：处理这 200 个字（prefill，一次前向）用了多久；之后每生成一个字（decode）平均多久。
   - 打印这两个数，并算出：prefill 平均每个字多久，decode 每个字多久，差多少倍。
   - 这两个数分别就是 TTFT（第一个字出来要等多久）和 TPOT（之后每个字的间隔）。

4. KV cache 占多少显存：按公式算（2 × 层数 × batch × 长度 × 每个字用几个数 × 每个数几字节），再用 torch.cuda.memory_allocated 实测，两个数对比。分别打印 batch=1、32、128，长度 = block_size 时的大小，并和模型参数本身占的显存比。

5. batching 的代价：有 cache，batch 取 1、4、16、64、256，打印：每秒总共生成多少字（吞吐）、每条请求生成完要多久（延迟）。看吞吐和延迟怎么此消彼长。

6. int8 量化：自己实现 weight-only int8（每个线性层的权重，按输出通道各算一个缩放系数，存成 int8 + scale；计算时再还原成浮点）。
   - 打印：量化前后模型文件大小、验证集 loss（和原来的比）、生成 5 首诗对比看看。
   - 也测一下速度，如果反而变慢了，解释为什么（提示：普通 PyTorch 没有 int8 矩阵乘的专用算子，还原那一步是额外开销）。

最后把所有表汇总成一份 results.md。
```

## 跑完后要能回答的问题
1. 有 cache 和没 cache 的输出一字不差吗？为什么 KV cache 不会改变结果？
2. batch=1 时 KV cache 提速多少？batch=128 时呢？为什么差别这么大？（和第 4 步的发现联系起来）
3. prefill 平均每个字比 decode 每个字快多少倍？为什么一次处理 200 个字反而比一个一个处理快？
4. batch=128 时 KV cache 占多少显存？和模型本身比谁大？如果换成 Qwen3-8B、32K 上下文，会发生什么？
5. batch 从 1 涨到 256，吞吐涨了多少倍？每条请求的延迟变了多少？如果你是推理服务的运维，你会怎么选 batch？
6. int8 让模型小了几倍？loss 损失多少？为什么"变小"不一定"变快"？
